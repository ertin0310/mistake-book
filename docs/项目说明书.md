# 项目说明书 · 错题本 + 间隔重复复习系统

本文按考核题目的四个口径组织：需求分析、设计与架构、功能说明、依赖环境与运行方式，另加一节算法与关键口径、一节未采纳与取舍、一节 AI 工具与模型使用说明。

文中每一处"已实现"都能指到具体文件；指不出来的写在第五节。表内数字均为编写本文时从仓库里现数、现跑得到的（`350 passed in 31.73s`，Python 3.12.10，2026-10-23）。

## 一、需求分析

### 1.1 服务谁

**要反复刷题、并且需要记住的东西不能丢的人**：备考学生（本项目演示数据按考研数学、英语、政治、专业课的题型风格造）、需要长期记住零散知识点的自学者。

他们手里通常已经有一个错题本（纸质或笔记软件里的），但那个本子只进不出——抄完就不再打开。问题不在"没记下来"，在**没人告诉他今天该复习哪几道**。

### 1.2 核心业务

把"错题"从一条静态记录变成一个**有排期的对象**：录进来的题做错一次，就进入复习队列；每复习一次，根据他自评的记住程度把下一次推到更远的将来；到期的题自动排进当天的队列，不用人规划。

服务对象与角色的划分：

| 角色 | 能做什么 | 数据边界 |
| --- | --- | --- |
| 未登录 | 只有注册、登录两个页面 | — |
| 普通用户 member | 录题、练习、复习、自评、统计、导入导出、提交知识点、软删与还原、改自己的设置 | 只看得到自己的私有记录；看不到别人的 |
| 管理员 admin | 用户能做的一切 + 独立布局的后台：科目管理、知识点审核、申诉收尾、建库自检 | **不穿透私有数据**：没有任何一处能查别人的错题、做题记录、复习流水、笔记、标签、收藏；后台四页都有测试盯着"读不到别人的私有题干" |

权限只有两层：登录了没有、是不是 admin。学习/复习模式**只决定侧边栏显示哪一组菜单，不是权限**（切到复习模式后直接敲学习网址照样能进）。

### 1.3 完整业务闭环是哪一条

这条链是在界面上用 HTTP 一步步走完并记进 `docs/提示词记录.md` 的，不是设计图上的设想：

```
注册 → 同意《站点协议》 → 录题 → 我的题目列表（按科目筛、翻页）
     → 练习并标记做错 → 这道题当天就进「今日复习」
     → 先作答 → 点「看答案」 → 四档自评 → 到期日按台阶往后推
     → 统计四张图 → 导出题目清单与复习记录 CSV → 原样导回、逐字节一致
     → 软删进回收站 → 还原（撞名先提示，不白屏） → 改设置
```

其中"做错自动入队"和"自评改期"两段，跨进程重启仍然成立（数据在 SQLite 单文件库里）。

## 二、设计与架构

### 2.1 三层强制分离 + 一个纯函数层

目标是一句话：**加功能、改数值、定位错误都只碰一个地方**。

| 层 | 目录 | 允许做什么 | 禁止什么 | 本项目的证据文件 |
| --- | --- | --- | --- | --- |
| 展示 | `src/web/blueprints/` + `templates/` | 收表单、调 service、渲染 | **出现 SQL 或算法规则即为不合格** | `src/web/blueprints/review_blueprint.py`（8 条路由，全层没有一条 SELECT） |
| 业务 | `src/services/`（12 个模块） | 编排步骤、判归属、抛语义错误 | 不写 SQL、不拼算法 | `src/services/review_service.py`（取今日队列、写复习流水） |
| 数据 | `src/data/repository/`（11 个模块） | **全站唯一允许写 SQL 的地方** | 不含业务规则 | `src/data/repository/base.py` |
| 纯函数 | `src/domain/`（13 个模块） | 算法与判据 | 不 import 数据库、不调 `datetime.now()`，日期与配置全部参数注入 | `src/domain/scheduling/ladder.py` |
| 配置 | `config/`（12 个模块） | 数值、文案、菜单、列规格、字段声明 | 不放业务规则 | `config/schedule.py` |

举一个真实的调用链，说明"任何改动只碰一层"落地成了什么：

改"评『没记住』之后间隔怎么变" → 只改 `config/schedule.py` 的 `LADDER_STEPS`；
算法本身 `src/domain/scheduling/ladder.py:27` 的 `next_state()` 不动；
service `review_service.py` 不动；
路由 `review_blueprint.py:117` 的 `rate()` 不动；
模板不动。

反向的例子也有：`src/domain/grading.py` 的判分是纯函数（两个字符串进、结果出），学习模式与复习页**共用同一份 `render_widget`**，不在两处各写一遍。

另外两条硬规矩：

- **一条请求一条连接**，连接与关闭都写在 `src/app.py` 的 `before_request` / `teardown_appcontext` 里；外键开关由 `src/data/db.py` 的取连接函数负责（见 4.6）。
- **全项目零个 `__init__.py`**，靠 Python 3 的命名空间包工作。这是定案，不是遗漏：一旦建了就得每开一个目录都记得补，漏一个就变成"一层有一层没有"的混合态，比全不建更难解释。唯一代价是 pytest 按文件名认测试模块，所以 `tests/` 里所有文件平铺在同一层且名字互不相同。

### 2.2 四种数据可见性范围（repository scope）

这是本项目防"数据泄露"的机制核心，全部实现在 `src/data/repository/base.py`，11 个 repo 继承它，**没有一个 repo 自己写 `WHERE user_id = ?`**。

| scope | 规则 | 用在哪些表 | 定义处 |
| --- | --- | --- | --- |
| `user` | 强制 `user_id = 看的人` | 错题、做题记录、复习流水、笔记、标签、收藏、导入会话 | `base.py:21` |
| `dict` | 所有人只读，写入要管理员 | 科目、协议正文 | `base.py:22` |
| `policy` | 由可见性判据决定（作者看得见自己被判的那条） | 知识点 | `base.py:23` |
| `named` | **只许两个具名读法，禁止混用一条 SQL** | 题目、题—知识点关联 | `base.py:24` |

**注入豁免名单**写在同一处：`NO_USER_INJECTION = {"subject", "agreement", "user"}`（`base.py:31`）。这三张表根本没有 `user_id` 列，基类给它们注入过滤条件就是写错。`user_agreement` 曾经误放进这份名单，后来按真实列结构取出来改走 `user` 范围——"谁在哪一版上点过同意"是私有记录。

为什么这么分，三个实际理由：

1. `question_bank.user_id` **可以为 NULL**（管理员以官方名义导入的题归属软件本身）。这类表一旦套上 `user_id = :viewer` 的通用过滤，官方题会凭空消失。所以它只能走 `named` 的 `mine` / `shared_pool` 两个具名读法，`read_named()` 还要求读法名必须事先登记在 `named_reads` 里（`base.py:170`），否则直接拒绝——"两个具名读法不许混用"是靠代码强制的，不是靠自觉。
2. 知识点是"提交即入池、管理员事后审"，被驳回的那条**作者自己看得见、别人看不见**，这不是 `user` 也不是 `dict`，只能是一条策略。
3. 声明与实际表结构对不上会**在构造时就报错**（`base.py:121` 的 `_check_declaration()`）：科目声明成 `user` 范围、`policy` 忘了声明实体、可见性判据里出现这张表没有的列，四种错法都有测试钉住。

`base.py` 还带三个全站通用件：

- `paginate()`（`base.py:213`）：每页 20 条（`config/settings.py` 的 `PAGE_SIZE`），**越界页码回落到最后一页**。全站只有这一份翻页，今日复习也走它——上限管"今天排多少道"，翻页管"一屏看多少道"，是两件事。
- 排序串过两道闸（`base.py:58` 的 `_safe_order`）：`ORDER BY` 不能参数化，所以形状必须是"列名 [ASC|DESC]"，且列名必须真的存在于这张表。`id; DROP TABLE`、`random()`、不存在的列一律拒。
- `create()`（`base.py:239`）只给 `user` 范围的表开，并且**把 `user_id` 一律覆盖成当前登录者**，调用方传别人的 id 也没用。

### 2.3 数据表设计（19 张 + 20 个索引）

建表脚本 `src/data/schema.sql`，由 `src/data/db.py` 在库文件不存在时自动执行。时间统一存 ISO-8601 文本；`due_date`、`reviewed_on`、`recorded_on` 这类"复习日"**只存 `YYYY-MM-DD`**，比较时用 `compute_review_date()` 的结果。

| # | 表 | 用途一句话 | 关键约束 |
| --- | --- | --- | --- |
| 1 | `user` | 账号 | `username` 唯一（存归一化后的值）；`password_hash` bcrypt；`role` CHECK 限 member/admin |
| 2 | `user_profile` | 有校验规则的正式资料 | `user_id` 唯一，一行一人 |
| 3 | `user_setting` | 偏好开关 | `UNIQUE(user_id, key)`，KV 结构，**加设置项不改表** |
| 4 | `agreement` | 协议正文 | `version` 主键；比新旧一律用整数 `seq`（字符串比较会得出 `SHARE-2 > SHARE-10`） |
| 5 | `user_agreement` | 谁在哪天同意了哪一版 | 只追加不改史；`version` 外键指向 `agreement` |
| 6 | `subject` | 科目（全站共享字典） | `status` 限 active/hidden；**永不物理删** |
| 7 | `knowledge_point` | 知识点，提交即 approved | `status` 三态；`reviewed_by` 为 NULL 表示管理员还没看过；**永不物理删** |
| 8 | `knowledge_note` | 一条知识点挂多条私人笔记 | 带时间戳，看得见自己理解的演进 |
| 9 | `question_bank` | 题库 | `type` CHECK 限 choice/blank/essay；`user_id` 可 NULL=官方题；`deleted_by`、`delisted_by`、`copied_from_question_id` 三个标记列；**永不物理删** |
| 10 | `question_knowledge_point` | 题—知识点关联 | **主键含 `user_id`**（谁标的归谁看；否则甲标过之后乙标同一个就撞主键） |
| 11 | `mistake` | 复习队列：某人对某道题的排期 | `entry_reason` 两态；`purged_at` 用于"过期封存"；**永不物理删**（流水账指着它） |
| 12 | `study_attempt` | 学习模式的做题信号 | `result`、`grade_source` CHECK（含 `manual`，简答题是自己判的）；不进回收站，改判就地更新 |
| 13 | `review_log` | 复习流水账 | **追加式、禁止 UPDATE、没有 `deleted_at`**；`rating` CHECK 1–4；带 before/after 六列与 `algorithm_version` |
| 14 | `tag` | 私人标签 | 软删可同名重建 |
| 15 | `tag_link` | 标签贴到对象上 | `UNIQUE(tag_id, target_type, target_id)` |
| 16 | `favorite` | 收藏，一张表管两类 | `target_type` CHECK 限 note/knowledge_point |
| 17 | `import_session` | 导入批次（也是草稿） | `target`、`format`、`status` 三组 CHECK；`format` 已给 `ai` 预留位 |
| 18 | `import_session_row` | 逐行的原文与报错 | `line_no` + `error_msg` + `status`，报错能精确到行就是这么存的 |
| 19 | `appeal` | 申诉与反馈 | `category` 四态；`status` open/handled；表已建、页面在规划中 |

索引 16 个 + 唯一索引 4 个。四个唯一索引都是 partial：

```sql
CREATE UNIQUE INDEX uq_kp_approved ON knowledge_point(subject_id, name_normalized)
    WHERE deleted_at IS NULL AND status = 'approved';
```
（`schema.sql:282`，另有 `uq_subject_active`、`uq_tag_active`、`uq_mistake_active`）

**为什么 partial 条件必须带状态，不能只看 `deleted_at`**：只看"没删除"的话，被驳回、被下架的行仍然白占着名字，于是同名永远建不回来；更难看的是查重会告诉乙"已经有了，请直接选用"，而那条**只有作者甲看得见**——乙既不许新建、又选不到，卡死在页面上。把状态写进索引条件之后，隐藏库和回收站里的行不占名字。这条由 `tests/test_visible_lock.py` 与 `tests/test_soft_delete_unique.py` 钉住。

**软删与"永不物理删"**：凡是会被别的行指着的东西一律不真删——`question_bank`、`knowledge_point`、`subject`，**外加 `mistake`**（`review_log.mistake_id` 每一行都指着它）。这四张表只进隐藏库或"过期封存"。这是能开外键约束的前提，也是"别人的引用不断线"的根本保证。到期清理只删两类：孤儿图片，和没人引用的私有行（笔记、标签连带它的关联、收藏、导入会话连带行）。`mistake` 到期时只打 `purged_at`，行留在库里，回收站底部一次 COUNT 显示"已过期 N 条"。

**"这次删除是谁按的按钮"必须存下来**：`deleted_by` 让回收站只放用户自己删的东西；管理员对别人的题只写 `delisted_by` + `delist_note`，**绝不写 `deleted_at`**。否则那条删除记录会落进作者自己的回收站，作者点一下"撤销删除"就把管理员的处罚翻掉了。

## 四、算法选型与关键口径

### 4.1 为什么用自研分级台阶表，SM-2 与 FSRS 为什么不采纳

采用固定台阶：`0 / 1 / 2 / 4 / 7 / 15 / 30 / 60` 天（`config/schedule.py` 的 `LADDER_INTERVALS`），自评四档决定进退（`LADDER_STEPS`）：评 1 升两级、评 2 升一级、评 3 **退一级**、评 4 归零并记一次 lapse。

- **不采纳 SM-2**：SM-2 的可调难度因子需要 0–5 六档的回忆质量打分，而本项目有意只给用户四档中文按钮（"熟悉啦/记住啦/一般般/没记住"）。把六档硬压成四档，映射就是失真来源；而且 EF 因子要落进 `mistake.ef` 这样的列，一旦这张列没有读者就成脏列（本项目已定：`mistake.ef` 不建）。
- **不采纳 FSRS**：它是拟合曲线模型，参数解释不了。这个作业要求"能读懂并解释 AI 生成的表结构与业务逻辑"，用黑盒模型会丢掉讲清楚的机会。
- **保留了接口**：`scheduling/base.py` 是抽象、`registry.py` 是注册表。将来要换算法是"新增实现类 + 注册一行"，调用方一行不改；每条流水还记了 `algorithm_version`，换算法之后历史仍分得清是哪套算法算出来的。

两个必须讲的细节，都是实现过程中发现原设计不成立才补的：

1. **"评『一般般』不能是原地不动"**：级数不动 → 间隔不变 → 下次到期日仍等于今天 → 这道题当天刷完立刻又回到今日队列，出不去。所以定成退一级，并夹在 0 与顶格之间（`ladder.py:19` 的 `_clamp`）。
2. **★ 补了一个原设计没堵完的洞**：台阶第 0 级的间隔是 0 天，于是"退一级退到 0"和"归零回 0"这两种情况都会**当天回队**，与第 1 条同一个理由。加了 `MIN_INTERVAL_AFTER_REVIEW = 1`（`ladder.py:37` 取 `max(台阶间隔, 1)`）：**评完之后到期日至少是明天**。新入队的错题不受影响，仍然当天可见——这是为了让人一眼看到"做错就进队列"。

### 4.2 「日界」的定义

复习不按自然日，按**复习日**。唯一入口是 `src/domain/clock.py:52` 的 `compute_review_date(moment, rollover_time)`：当前时刻不早于"今天的切换时刻"就算今天，否则算昨天。全项目不许出现第二处 `datetime.now()`，也不许有第二个日历概念——热力图、近 30 天趋势、"今日"、做题记录的 `recorded_on` 全部用同一个值。

用户可以设每日切换时刻，默认 `00:00`。改动何时生效由 `decide_rollover_change()`（`clock.py:86`）判：**改的时刻还没过原时间点 → 当日生效；已经过了 → 次日生效**。理由是晚上八点之后改时刻若立即生效，"今天"会退化成"昨天"，当天已经刷完的题会重新出现一遍。待生效的值与生效日期分别存在 `review_time_pending` 与 `review_time_pending_from`，后者**存日期不存时刻**。

**一条必须写清的行为**：把切换时刻改成**次日生效**这一条是防"当天已刷完的题重新冒出来"的，而**当日生效**的条件是"提交那一刻还没过**原**时刻"（`decide_rollover_change`）。默认 `00:00` 时"现在早于今天的 00:00"恒不成立，所以**从没改过时刻的用户，改设置一律次日生效**——这条分支走不到只是默认值的推论，不是全局规则：原时刻一旦不是 `00:00`，在它被跨过之前改动就当日生效。这个默认值行为由 `tests/test_clock.py` 的 `test_default_rollover_always_defers_to_tomorrow` 钉住（0:30 / 8:30 / 14:30 / 23:30 四个时刻各跑一遍，都断言不立即生效），当日生效与次日生效两条也各有一条用例（同文件 `test_change_before_cut_off_applies_today` / `test_change_after_cut_off_applies_tomorrow`，原时刻 `20:00`、14:00 改判当日、21:00 改判次日）。README 第七节写的是同一件事。

时区本期**只存值、不参与计算**；值为空或认不出来时一律回落本机时间，且这个回落只在 `clock.py` 一处判。二期启用换算时改的地方就是取时间那一个函数。

### 4.3 判分口径

判分是纯函数，全在 `src/domain/grading.py`（20 条用例覆盖）。四条口径：

| 口径 | 定成什么样 | 为什么 |
| --- | --- | --- |
| 归一化 | 忽略大小写、全半角、空格；**标点不忽略** | `1, 2` 与 `12` 是两回事，把标点也吃掉会把错的判成对的（`grading.py:7`） |
| 选择题 | 多选必须**全对**才算对 | 少选即判对不符合考试口径，也更容易掩盖没掌握 |
| 填空题 | 外层数组=第几空，内层数组=该空可接受的答案；界面上**同一空的多种写法用竖线** `光滑\|无摩擦` | `grading.py:69` 的 `grade_blanks()` |
| ★ 斜杠永不参与切分 | 斜杠不是分隔符 | 这是**判分错误而不是显示错误**的源头：若同空多答案用 `/` 分，数学答案 `1/2` 会被劈成 `1` 和 `2`，于是学生填 `1` 被判对 |

竖线语法只活在一个地方：手动录入表单和 CSV 的简写入口，由 `normalize.to_canonical_json()` 一次转成标准 JSON。**存储层、导出的 CSV、JSONL 通道里只有标准 JSON**，一条规矩没松；所以题干和解析里的 `|x|`、`a|b`、行列式、换行、逗号、引号统统是纯文本，永不拆。填空题按"一行一个空"写。

耗时只用于**默认预选**，绝不自动提交：`preselect_rating()`（`grading.py:106`）拿本次耗时与该科目历史耗时**中位数**比，倍率带在 `config/schedule.py:33`（`<0.6` / `0.6–1.2` / `1.2–2` / 更慢），映射表 `PRESELECT_MAP` 在 `config/prompts.py:26`；**该科样本不足 10 条就不预选**（`MIN_DURATION_SAMPLES`），强制用户手点；单次耗时超 1800 秒按上限截断，防一次挂机把整科中位数拖飞。提交时到底是系统预选还是人改判，记在 `review_log.rating_source`（`user_override` / `duration_default`），所以"人改判率"是能统计出来的。耗时是**建议性指标，不是判定性指标**。

改判"我其实答对了"时，只收回那条**自动入队且一次都还没复习过**的错题（`entry_reason='marked_wrong'` 且 `review_count=0`），复习过的不收回——真实学习轨迹不能替用户抹掉。

### 4.4 导入与导出为什么共用同一套序列化

链路是：上传 → 清洗 → 解析 → 逐行校验 → 预览 → 确认入库，**两步式防误操作**，实现分别在 `src/data/importers/`（清洗与解析）与 `src/services/import_service.py`（校验与入库）。

要让"导出的文件原样导回、逐字节一致"成立，前提是**库里只允许一种 JSON 写法**。这件事是做到导出那一步才真正成立的：`seed.py` 原先直接 `json.dumps()` 写出去是 `{"letters": "AC"}`（冒号后带空格），而列内规范化函数产出的是 `{"letters":"AC"}`，两套写法并存时 round-trip 从根上不成立。改法是让 **seed 也走同一个 `to_canonical_json()`**。

导出与导入之间只允许一处改名：库里叫 `options_json` / `answer_json`，列规格里叫 `options` / `answer`，这个翻译只写在 `src/services/export_service.py` 的 `_question_rows()` 里，**值本身一字不改地写出去**（`options` / `answer` 两列直接放 JSON 字符串，`csv.writer` 因内含逗号自动加外层引号，`csv.reader` 读回自动剥掉——结构靠 JSON 的引号，不靠字符分隔符）。

两份用例把这层地基盯住：`tests/test_csv_roundtrip.py`（导出再导回一致）与 `tests/test_csv_parity.py`（**恶意用例**：题干带 `|x|`、换行、中文逗号；答案带 `1/2` 与转义引号；解析带 `|||`）。另有一条 `test_shipped_samples_import_cleanly` 盯着"样例文件与列规格同步"——以后加列忘了改 `import-templates/` 里的样例，测试立刻红。

导入的两个体验设计：

- **报错精确到文件里的真实行号并点名哪一列**。七列的 CSV 里光说"有空着"等于没说，所以文案是「列「stem」必填项不能空着。」
- **错题引用了不存在的知识点**时不是一句"导入失败"，而是列出缺失清单 + 给模板下载 + 一颗「顺手一起建了」的勾，勾了就在同一事务里先建知识点再建题（知识点本来就是提交即入池、事后审，顺手建不破坏任何规矩）。本批题目暂存成 `import_session` 草稿，用户回来一键重跑预检，**不重填不重传**。

### 4.5 越权为什么一律 404 而不是 403

403 会**承认"这条记录存在，只是不归你"**，等于把资源 ID 的有无变成可探测的信息；一个挂着别人 ID 的链接，用 403/200 就能反推哪些错题存在。404 把"别人的行"与"不存在"合成同一件事，service 层据此只有一种分支（`base.py:192` 的 `get()` 对别人的行返回 `None`）。

文案也按这个口径写：`config/prompts.py` 的 `NOT_FOUND` 是"这条记录不在你的错题本里。可能是链接串了，也可能它已经被移入回收站。"——**不提"别人"两个字**。

这一步（越权回归）真正的产出是查出了四个"能跑但会撒谎"的 bug，都已修：

1. `UPDATE ... WHERE user_id=:viewer` 打空（改动 0 行）之后，路由照样提示"改好了""已放进回收站"。补了 `question_service.require_mine()`：先确认是自己的再动笔。
2. **导入的批次号是表单字段，谁都能改**。原来 `commit()` 不判归属，等于把"确认导入"按钮开给全仓库；现在先判过，不是自己的一律 404。
3. 回收站还原别人的行原来给 400，按本节口径改成 404；同一段里还残留一处 service 层的裸 SQL，违反"SQL 只在数据层"，已收进 repo。
4. **把"能看见"当成"能用"**：知识点查重用过可见性口径，于是作者自己会被那条被驳回的死行顶掉——甲被驳回 → 甲再提交同名 → 系统提示"已经有了，去选用一条" → 那条是死的，甲永远改不回来。新增独立口径 `USABLE = status='approved' AND deleted_at IS NULL`。**"能看见"与"能用"是两份定义，各写一份，不许互相顶。**

可见性判据在代码里有两份，这是**选定的方案，不是失误**：一份是 `src/domain/visibility.py` 的三个具名纯函数（`knowledge_point_visible` / `subject_visible` / `question_visible`，外面套一个只做分发、不含判断逻辑的 `is_visible()`）；另一份是 `base.py:39` 的 `VISIBILITY_CLAUSES`，即数据层用的等价 SQL 条件。为什么必须有两份：过滤要发生在**取数那一刻**，否则翻页总数不对、不该读的行会先进内存。一致性由 `tests/test_visibility_policy.py` 穷举判据的取值组合、逐格比对两边，一边漂移就红。已用测试钉死的两条口径：**被官方收起的题对所有人不可见，包括作者本人**（作者走失效页与申诉，不靠"自己还看得见"）；**软删的知识点连作者也不可见**（否则回收站和选用下拉会同时列出两条同名）。

知识点不做近似匹配：「牛顿第二定律」和「牛顿第二定律的应用」是两条，有意为之。

### 4.6 一条容易写错的外键设置

`PRAGMA foreign_keys = ON` **写在每次取连接的函数里**，不能只写在 `schema.sql`：这个开关是每条连接私有的、不会被记住，而建库脚本一辈子只在库文件不存在时执行一次。只靠脚本的话，之后每个请求的连接其实都没有外键约束，本项目花大力气保证的"引用永不悬空"当场失效。

| 用户之间点名互相举报 | 不做 | 改为统一的申诉与反馈通道，管理方单向处理、**不向被处置者暴露提交人**，避免变成对骂场 |
| 复制式总题库 | 不做 | 总题库是引用视图；只有"作者已撤走"这一种情况才给一次性复制的出路 |
| 题目内容快照与版本 | 不做 | 改题目内容直接生效 |
| 知识点审核前置 | 不做 | 改成提交即入池、管理员事后审 |
| 后台高级功能（数据看板、公告、批量操作、操作日志）、细粒度权限 | 不做 | 本期只有 member/admin 两级 |
| MySQL / PostgreSQL、Django、FastAPI、Node + Express、Spring Boot、本地模型、桌面 GUI | 不做 | 全部与"评审 clone 下来一条命令就能跑"或"分层讲得清"冲突 |
| 用标志位表示暂停 | 不做 | 每条恢复路径都要记得改回来，漏一处就是永久幽灵数据；改成 JOIN 不成立即自动停排、恢复即可见 |

### 5.2 原定要做、本期没做完的功能（数据层状态逐项标明）

下面这些**逐项核对过数据层与接口状态**；标"缺什么"的就是评审在界面里点不到的部分：

| 功能 | 数据层与接口 | 缺什么 |
| --- | --- | --- |
| 题目共享与《共享须知》三态弹窗 | 已做完：`/study/share/<id>` 先验归属再弹正文，三颗按钮分别是"仅本次同意并共享 / 同意并授予长期授权 / 取消"；长期授权绑 `agreement` 版本号（按整数 `seq` 比），正文升版后重弹；「取消共享」不影响已存题的人 | 录题表单上"录完直接共享"那一格勾选（共享要在列表里逐道题点） |
| 「已失效的题目」页与「另存为我自己的」 | `delisted_by`、`delist_note`、`copied_from_question_id` 列已建；收起与软删的题已在取队列 SQL 里被排除 | 那一页本身，以及复制题目 + 复制知识点关联 + 把排期指向新行的逻辑 |
| 私人笔记、标签、收藏、题目图片 | `knowledge_note`、`tag`、`tag_link`、`favorite` 四张表已建，唯一约束已按"软删不占名字"设计；`image_path` 列与上传目录常量、扩展名白名单、5 MB 上限都在 `config/settings.py` | 全部页面；图片上传与带鉴权的读取路由 |
| 管理后台 | 已做完四页：概览、科目管理（新建/改名/停用，**没有删除按钮**）、知识点审核（通过/驳回带原因/下架/直建）、申诉队列（收尾必须写回复），另加一页建库自检 `/admin/diagnostics`（原在首页，普通用户现在 403 进不去）。后台是**独立入口 + 独立布局 + 必须登录且必须是管理员**，侧边栏只留一条「后台」入口 | 题目收起/恢复、官方题批量导入、用户与角色管理这三页 |
| 申诉与反馈 | 已做完：`/appeal/` 一张表单四类，提交后在同一页看状态与回复（不做站内信）；后台队列收尾必须写回复；`seed.py` 灌了几条真实样例 | 无 |
| 拍照识题（AI 接入） | `settings.ai_enabled()` 与每人每天 20 次的限额常量已就位，AI 的输出要走的清洗与 JSONL 通道已经能用（`import_session.format` 的 CHECK 里 `ai` 已预留） | 接口封装、上传路由、提示词模板包 |

本期已实现并有测试覆盖的部分：选择题与填空题的自动判分、耗时预选（口径见 4.3，`tests/test_grading.py` 已有 20 条）。

与"接不接 AI"这个决定本身有关的反复也记在 `docs/提示词记录.md` 里：一开始定为程序内一行 AI 调用都不写，后来因为"CSV 列要人手写 JSON 太难用"改成**预留接口与配置位、功能本期不实现**，预留的前提是默认关闭 + 三条硬保护——没配密钥时入口整块不出现（不是灰掉）、调不通不许崩且必须还有第二条路、AI 的输出不许直接进数据库必须走预览。理由不是"违规不违规"，而是"评审没配密钥时功能当场是坏的"这件事更实际。

### 6.1 依赖清单（5 个，`requirements.txt`）

| 依赖 | 版本 | 干什么 |
| --- | --- | --- |
| `Flask` | 3.1.3 | Web 框架与 Jinja2 模板；不用它的任何扩展 |
| `bcrypt` | 5.0.0 | 密码哈希，绝不明文存 |

| `pytest` | 9.1.1 | 跑 350 条用例 |

依赖刻意保持少：**评审 `pip install` 的东西越少，"clone 就能跑"这条越稳**。`.env` 的读取就是为此自己写了十几行（`config/settings.py` 的 `_read_dotenv`），而不是引一个 `python-dotenv`。

### 6.2 运行环境与命令

- Python 3.10 以上，本项目在 **3.12.10** 上验证。
- 数据库是单文件 SQLite，不需要装任何数据库服务，不需要 migration 命令，不需要构建前端。

```
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python run.py          # 打开 http://127.0.0.1:5000
.venv\Scripts\python -m pytest       # 跑全部用例
```

启动时程序自己完成：建 `var/` 与 `var/uploads/` → 库文件不存在就执行 `schema.sql` 建 19 张表 → `user` 表为空时灌演示数据。`run.py` 里 `debug=False`、端口固定 5000、只绑 `127.0.0.1`。

要恢复到干净状态：删掉 `var/` 再启动。

### 6.3 环境变量（只写方法，仓库里没有值）

| 变量 | 必需 | 说明 |
| --- | --- | --- |
| `SECRET_KEY` | 建议配 | 会话签名密钥。不配时程序自动生成一个随机值存进 `var/.secret_key`，重启后仍有效。配置方法：复制 `.env.example` 为 `.env` 填值；生成一条 `python -c "import secrets; print(secrets.token_urlsafe(32))"` |
| `AI_API_KEY` | **可留空** | 规划中的拍照识题用。留空则那块入口整块不出现，其余功能完全不依赖它 |

`.env` 被 `.gitignore` 拦住，仓库里只有模板 `.env.example`；`var/`（库、图片、生成的密钥）同样不进仓库，**数据与图片的备份自理**。

## 七、AI 工具与模型使用说明

本项目全程使用 **Qoder Desktop**（AI 编程 IDE 的 Agent 模式）协作，模型为 Claude 系列。与 README 第十节同源。用法不是对话式补全，而是把文件读写与命令执行交给智能体：读方案、改文件、跑 `pytest`、以只读方式连库数数，都通过工具调用完成，过程留在 `docs/提示词记录.md` 里。

### 7.1 会话分工

同一个仓库上先后开过五条会话，各管一段，写入权互不重叠：

| 会话 | 阶段 | 负责什么 | 产出 |
| --- | --- | --- | --- |
| 分析考核题目任务二 | 选题（10-18） | 读题目、定选题与技术栈 | 需求与选型结论 |
| 阅读题目与方案查问题 | 方案复核 | 按"会不会当场白屏"逐条挑问题 | 问题清单 |
| 审阅方案可行性 | 架构定稿 | 对账施工单、定分层与可见性口径 | 表结构与分层口径 |
| 配合解题（施工主线） | 施工（10-21 起，即记录里的 A-1 之后） | 按档写代码、跑测试、修 bug、维护提示词记录 | `src/`、`tests/`、`docs/提示词记录.md` |
| 交付文档 | 收尾（10-23） | 只写 `README.md` 与本说明书，不碰代码 | 两份文档 |

施工主线与文档线是**并行**的两条：一条改代码，一条写文档，双方只碰自己的文件。本文里的每个数字都是写文档这条线自己现跑、现数得到的，不向施工线要。

### 7.2 AI 用在哪些环节

| 环节 | 怎么用 | 例子与出处 |
| --- | --- | --- |
| 设计对账 | 把方案整份读进去，要求按"会不会当场报错"排序逐条挑问题，不接受泛泛评价 | 方案复核与架构定稿两条会话；进入施工后的同类做法见 A-1：一次报出三处会影响大局的问题，然后停下等指令 |
| 实现与排错 | 报错原文整段贴回，要求先解释成因再改，改完必须重跑并报实测数 | A-52：三百多条用例全绿，回收站页却 500——那个类不继承基类、属性名对不上，而库里没有软删错题时这条分支走不到；补了一条专门踩该路径的用例 |
| 复核 AI 自己的输出 | 每个数字现跑现数；发现与事实不一致当面说，不顺着写 | 曾把首页说成建库自检页、把切换时刻"当日生效"的条件写成新时刻而非原时刻、把提示词记录编号引串，三处均当场改回 |
| 写交付文档 | 需求、表设计、路由清单、算法取舍由 AI 起草，人逐节核对后才算数 | 本说明书与 README |

### 7.3 三条硬性边界

| 边界 | 做法 | 有没有违反过 |
| --- | --- | --- |
| 不越命令 | 不擅自加功能、不改相邻机制、不提前动手；每轮结束停下等指令 | 违反过一次：把"缺的东西补一下"听成"把第 0 档缺的文件全写出来"，一口气生成 20 个文件，完整回滚（A-3，自查在 A-16） |
| 一步一演示 | 每个阶段必须给出可粘贴的命令和"点哪里能看到"，演示不出不算完成 | 没有违反的记录；各步末尾的复测数字与逐页 HTTP 实测都留在记录里 |
| 决定权在人 | 权限、合规、接不接外部 AI 这类取舍，AI 只列选项与利弊 | 接 AI 一事反复两轮（先定不接、后改默认关闭地接），反转与理由如实记在 5.2 与提示词记录里 |

因此本项目的 AI 用法是"**能查错的手，不是拿主意的脑子**"：算法选型、19 张表的结构、权限模型、本期不做的清单，都是人拍的板。

### 7.4 产品运行时不调用 AI

软件本身**没有一处 AI 接口调用**。`AI_API_KEY` 是给二期"拍照识题"预留的：`config/settings.py:79` 的 `ai_enabled()` 只判断这个变量有没有值，留空时那块入口整块不出现，其余功能不受影响；`import_session.format` 的 CHECK 里预留了 `ai` 值，导入的预检与预览通道已经能用，但生成端未接。本期没做的理由见 5.2。

### 7.5 这些说法在哪儿复核

`docs/提示词记录.md` 有 55 条按时间编号的条目（A-1 至 A-55），每条都记录了当时的提示词与 AI 输出摘要，有报错的条目另附报错原文和修法。上文点名的三处可直达：越令回滚 A-3 与自查 A-16、写视图层前被拦 A-42、全绿却 500 的页面 A-52。评审可逐条对照本文引用的文件与行号。
